为什么需要这份规范

工作台的所有结论都由数据重算：技术基线来自等级问卷与视频评估，负荷来自训练日志，准备度来自每日打卡与穿戴数据，体能域来自测评，瓶颈来自三域与目标的差距。没有数据就不会伪造分数——对应领域显示「未评估」，诊断页会明确列出缺口。

泛化的两类输入① 真实采集的数据；② 可编辑的规则配置（技术库、题目、动作、阈值、权重）。两类都会改变清单、等级、诊断与计划。
采集器的角色只负责低摩擦、离线、多人地收集数据，不做评分。评分与决策统一留在工作台，避免两套口径。
配置包的作用工作台导出配置包 → 采集器导入，保证两端的题目、测评项、技术名完全对齐，合并时不会错位。

质量控制规则

合并策略
  • 按 id 去重；无 id 时按 date（mind / wear / tests）或 week 去重
  • 同键重复时后导入的覆盖先前的，演示数据永不被采集包覆盖
  • 每次导入在 sources 留痕：来源名称、日期、条数
  • 批量包 bwb.collect.batch 会逐人递归合并
异常与缺失
  • 合理范围：RPE 1-10、时长 0-600 min、疼痛 1-5、睡眠 0-14 h
  • 重复日期、超范围值会在「数据质量报告」列出
  • 缺失训练日志 / 打卡 / 测评时，对应领域显示「未评估」，不填占位分
  • 演示数据带 demo:true 与 [演示] 标记，可一键清除且不影响真实数据

多人、命名与同步

档案划分
采集器为每位运动员建一个独立档案（各自独立的 logs / mind / wear / ...）。同一浏览器可切换多人，导出时选「当前运动员」或「全部运动员」。
ID 规则
档案建立时生成稳定 id；采集包携带 subject.name + subject.id。重命名不会改变 id，合并仍按数据行的 id / 日期去重。
文件命名
bwb-collect-姓名-日期.json、bwb-collect-all-日期.json、bwb-config-日期.json；CSV 分包为 bwb-类别-姓名-日期.csv。
同步流程
① 工作台「规则配置 → 导出配置包」→ ② 采集器「导出与同步 → 导入配置包」→ ③ 采集数据 → ④ 导出采集包 → ⑤ 工作台「数据接入 → 导入采集包」→ ⑥ 今日 / 诊断 / 等级页自动重算。
离线与隐私
全部数据仅在本机浏览器 localStorage，不上传服务器；换设备用 JSON 导入导出迁移。视频本体不入库，只记录文件名与姿态 JSON 关联。

泛化验收清单

改完数据或配置后逐项核对
  1. 输入敏感性：工作台「规则配置 → A / B 灵敏度验证」，两组不同输入应有至少 7 项输出发生变化（准备度、ACWR、三域得分、主要瓶颈、清单首项、负荷目标、预警数）。
  2. 配置敏感性：修改任一算法参数（如降载线、ACWR 高风险线、恢复权重），「实时输出」卡片应立即变化；修改技术库 / 问卷 / 测评基准后，内容库页、等级页、今日清单都应反映新条目。
  3. 空数据诚实性：清空数据后，诊断页应显示「数据不足，暂不给出确定性结论」并列出缺口，不得出现基于默认分数的结论。
  4. 采集闭环：采集器录入 A 与 B 两份不同数据 → 分别导入工作台 → 今日清单与瓶颈结论不同。
  5. 去重与留痕：同一采集包导入两次，记录数不增加；数据接入页能看到导入来源与条数。
如果某一步没有变化，说明该输出仍依赖写死的常量——应在「规则配置」里检查对应参数或内容库是否真正被引用。
